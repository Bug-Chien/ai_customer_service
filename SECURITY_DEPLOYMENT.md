# Security deployment checklist

This change is a coordinated application and database update. A code deployment alone does not close the old Data API access. Do not resume a paused database until its grants and policies have been reviewed.

1. Identify the exact production Supabase project and Netlify site. Export the current schema, grants and policies, and make a backup. Inspect `pg_policies`, `information_schema.role_table_grants`, exposed views and callable functions for alternate access to settings.
2. Identify the intended administrators. Using a trusted Supabase administrator or server-side Auth Admin API, set only those users' `app_metadata.role` to `admin`. Never use user-editable `user_metadata`. Preserve other app metadata when setting this field. Require those users to sign in again to refresh their JWTs. This change does not automatically promote any existing user.
3. Verify the existing server-only `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`. Keep the service role key out of browser-prefixed variables. Deploy this branch to a protected preview, with a separate test database.
4. In that test database, apply `supabase_schema.sql`. The script preserves data, removes the known broad policies, revokes direct browser privileges on settings and processed events, restricts user state changes to admins, and restricts knowledge bucket writes to admins. Inspect for other pre-existing permissive policies before production; this script does not indiscriminately delete custom policies.
5. Test anonymous, ordinary, forged-user-metadata and administrator sessions. Direct `settings` REST reads and writes must fail even for admins. Only the server settings endpoint should work for admins, and GET/PATCH responses must never contain stored secret values. Verify blank inputs preserve credentials and replacement credentials remain write-only.
6. Test LINE webhook signature validation, event deduplication, AI replies, handover, admin settings saving, file upload and state reset. `knowledge_base` deliberately remains a public bucket for compatibility: upload only public material. Private knowledge needs a separate private-bucket and signed/server retrieval implementation.
7. Schedule the coordinated production update. First restrict the database; old admin pages will stop reading settings until the new code is deployed. Deploy and repeat the checks. If UI recovery is required, repair/forward-deploy the app; do not restore the overly broad secret-table grants as a rollback.
8. If investigation confirms that credentials were stored behind the old permissive policy, rotate those credentials at each provider, update the server settings and verify service operation before revoking old credentials. Review provider usage and access logs; the code change cannot prove whether credentials were previously read.

The API validates the bearer token using Supabase Auth `getUser` on every request and uses current server-controlled app metadata for authorization. Client gating is only a user experience measure. RLS on `user_states` and storage reads JWT claims, which can remain stale until refresh/expiry: plan session revocation and short token lifetimes when removing admin access.

References: [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [getUser](https://supabase.com/docs/reference/javascript/auth-getuser).
